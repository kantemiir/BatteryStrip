# Устройства: что известно о чтении заряда

Проверено на компьютере пользователя 10.11.2026. Инструмент — `research/hid-probe/hidprobe.cs`.
Он только читает: перечисляет HID-коллекции и слушает входящие отчёты, в устройства ничего не пишет.

## Мышь Lamzu — приёмник 25A7:FA7C

Опознание: в `C:\Program Files (x86)\LAMZU Gaming Mouse\Cfg.ini` записано `VID=0x25A7, PID=0xFA7B, PID2=0xFA7C`
(FA7B — по проводу, FA7C — через приёмник). Строка продукта приёмника — «2.4G Wireless Receiver».
Чипсет и протокол — COMPX, тот же, что у Ajazz, Attack Shark, VXE и Thunderobot.

HID-коллекции интерфейса MI_01:

| Коллекция | Usage page | Отчёты |
|---|---|---|
| COL02 | 0xFF03 | вход 0x02, 8 байт |
| COL05 | 0xFF01 | вход 0x09, 17 байт ← ответы мыши |
| COL06 | 0xFF04 | feature 0x06, 8 байт |
| COL07 | 0xFF02 | feature 0x08, 17 байт ← команды мыши |

**Пассивное наблюдение.** Официальная программа `OemDrv.exe` раз в 30 секунд спрашивает заряд.
Ответ приходит входящим отчётом на COL05, и его получают все, кто открыл коллекцию на чтение:

```
09 04 00 00 00 02 1E 00 00 00 00 00 00 00 00 00 28
│  │  │  └──┤  │  │  │                          └ контрольная сумма
│  │  │  адрес │  │  └ зарядка: 0 — нет
│  │  статус 0 │  └ заряд: 0x1E = 30 %
│  команда 04  └ длина данных: 2
отчёт 0x09
```

Контрольная сумма: `(0x55 − сумма байтов 0..15) & 0xFF`, включая номер отчёта. Для строки выше 0x55 − 0x2D = 0x28, сходится.

**Запрос** (в `OemDrv.exe` есть строки `HidD_SetFeature` и `GetPower: nPower=0x%x, bCharging=0x%x`):

```
08 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49     (feature-отчёт 0x08 на COL07)
```

Формат запроса одинаково описывают три открытых проекта:
[AreYouLowBattery](https://github.com/ryan-mant/AreYouLowBattery) (MIT по pyproject),
[omarchy-ajazz-mouse](https://github.com/Alanus96/omarchy-ajazz-mouse) (MIT) и
[mouse-battery-reminder](https://github.com/245582001g-oss/mouse-battery-reminder) (MIT).
Сами мы его ещё не отправляли.

- Если байты 5–7 ответа нулевые, мышь спит: показываем последнее известное значение.
- На кабеле при 100 % мышь иногда присылает «95 %, заряжается» (подзарядка). Нужна защёлка: увидели 100 % — до отключения кабеля держим 100 %.
- Никогда не отправлять команды 0x07 (SetEEPROM) и 0x08 (GetEEPROM): первая меняет настройки мыши.

## Наушники Logitech G435 — приёмник 046D:0ACB

Строка продукта — «G435 Wireless Gaming Headset». Интерфейс MI_03:

| Коллекция | Usage page | Отчёты |
|---|---|---|
| COL01 | 0x000C (мультимедиа) | вход 0x03 |
| COL02 | 0x000B (телефония) | вход 0x05 |
| COL03 | 0xFFC0 | вход 0x06 (8 байт), выход 0x06 (515 байт), feature 0x06 (64 байта) |
| COL04 | 0xFFC3 | вход 0x34 (21 байт), выход 0x34 (3 байта) |

HID++ здесь нет: нет коллекций 0xFF00 или 0xFF43 с отчётами 0x10 и 0x11. Поэтому Solaar и HeadsetControl
эту гарнитуру не поддерживают. Приёмник 0ACB — мост Realtek со своим протоколом. За 150 секунд прослушки
гарнитура сама ничего не прислала.

Единственный известный способ чтения — [logitech-g435-battery](https://github.com/deddroid/logitech-g435-battery) (MIT),
протокол описан в [статье endes](https://dev.to/endes/usb-hid-down-the-rabbit-hole-logitech-g435-dongle-33if):

1. перевести мост в «режим загрузчика»: feature `06 01 03`;
2. проверить связь с гарнитурой (`PA`-команда 0xE3), режим (0xE0) и при необходимости переключить режим (0xE1 01);
3. запросить напряжение (OTA 0x31), получить милливольты, перевести их в проценты по кривой Li-Po;
4. выйти из режима загрузчика: `06 08 03`.

Минусы:
- звук пропадает примерно на секунду при каждом чтении;
- команда 0xE1 меняет состояние приёмника;
- признака зарядки нет;
- под Windows автор этот способ не проверял.

Соседние команды того же моста опасны (OTA, стирание NVDS), а после `GET_RSSI` приёмник зависал.
**Без отдельного согласия пользователя не используем.**

### Требование пользователя (10.11.2026): «100 % рабочий способ, всё или ничего»

Что выяснилось при углублённом чтении источников:

- Официальной программы, которая показывает заряд G435, нет: G HUB эту гарнитуру не поддерживает.
  Протокол получен разбором официальной утилиты обновления прошивки. Запрос заряда — её проверка перед обновлением.
- Гарнитура не присылает заряд сама, уведомлений о заряде в протоколе нет. Назначение коллекции 0xFFC3 (отчёт 0x34) неизвестно.
- Команды «заряжается ли» нет. Во время зарядки напряжение завышено, и оценка процентов тоже.
- Проценты — всегда оценка по напряжению (4,2 В = 100 %, 3,4 В = 0 %), а не число от самой гарнитуры.
- Остановка звука на время служебного режима неизбежна. У автора на Windows чтение идёт по расписанию,
  без проверки тишины; на Linux он ждёт тишину.
- Сообщений о «убитых» приёмниках нет (трекер проекта пуст). Зависание лечится переподключением приёмника.
- Команда 0xE1 01 («режим 1») входит в обычную процедуру сопряжения, так что приёмник, скорее всего, уже в режиме 1.

Тестовая утилита: `research/g435-probe/g435probe.cs`. Без `--run` ничего не отправляет.
Сухой прогон 10.11.2026 нашёл приёмник (feature-отчёт 64 байта), кадры совпали с источником,
разбор ответов проверен на записанных автором примерах.

### Тест на приёмнике пользователя (10.11.2026, с его согласия)

Способ работает под Windows через `HidD_SetFeature` / `HidD_GetFeature` на коллекции 0xFFC0.

- Вход в служебный режим и выход подтверждаются за 4–8 мс (`06 5A`).
- Каждая `PA`-команда занимает около 430 мс: столько приёмник ждёт, прежде чем подтвердить её.
- Приёмник находился в «режиме 0». В нём запрос заряда до гарнитуры не доходит, поэтому перед чтением
  ставим режим 1 (`E1 01`), а после чтения возвращаем 0 (`E1 00`) и проверяем. Возврат подтверждён.
- Ответ на запрос заряда: `06 50 49 01 C6 EA 85 31 00 07 00 06 84 00 BD 0F 00 00`, то есть 0x0FBD = 4029 мВ ≈ 83 %.
  Индикатор на гарнитуре в этот момент зелёный (31–100 %).
- Полная последовательность с проверками длилась 2,9 с. Минимальная
  (вход, связь, режим 1, заряд, режим 0, выход) займёт около 1,8 с.
- Аудиоустройства G435 (воспроизведение и микрофон) во время чтений из Windows не пропадали, сеансы звука не обрывались.
- Тишину и занятость микрофона можно определять через Core Audio: `research/audio-probe/audioprobe.cs`.
  Устройства звука и HID-интерфейс приёмника связываются по общему Container ID.

**Серия из 10 чтений с интервалом 20 с: 10 из 10 успешно.** Напряжение 4017–4029 мВ (82–83 %), разброс ±6 мВ.
Каждый раз режим возвращён в 0 и получено подтверждение выхода `06 5A`. Ошибок и таймаутов нет.
Во время серии через наушники тихо играл звук из Chrome; пользователь пропадания звука при первом чтении не заметил.
Слышно ли пропадание при обычной громкости — ещё не проверено.

Критерий «всё»: 10 чтений подряд без сбоев, приёмник каждый раз выходит из служебного режима,
значение сходится с индикатором на гарнитуре, чтение в тишине не слышно. Иначе — «ничего»: G435 в полоске не показываем.

Через Bluetooth G435 сообщает заряд стандартно (так пишет Logitech), и Windows показывает его в «Параметрах».

## Приёмник 8BitDo — 2DC8:301C

Строка продукта — «IDLE», одна vendor-коллекция 0xFFA0 (вход 0x02, выход 0x81, по 64 байта).
Это приёмник без подключённого геймпада: когда геймпад включён, приёмник переподключается с другим PID
(например, 310A у Ultimate 2C в режиме XInput). Модель и способ чтения заряда определим, когда геймпад включат.
Если он работает как проводной Xbox 360 (XInput), Windows заряд не знает.

## Клавиатура — приёмник 0416:C345

Строка продукта — «Gaming Keyboard». Коллекции клавиатуры, мыши, мультимедиа и vendor 0xFF1B (64 байта, отчёт 0x01).
Пользователь её не упоминал. За время прослушки ничего не прислала.

## Bluetooth

Сопряжено устройство «Kani» (аудио, AVRCP), сейчас не подключено. Заряд Bluetooth-устройств Windows хранит
в свойстве устройства `{104EA319-6EE2-4701-BD47-8DDBF425BBE5} 2`. Это общий путь для любых наушников и мышей по Bluetooth.
